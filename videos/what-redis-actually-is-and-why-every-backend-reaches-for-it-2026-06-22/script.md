One program sits underneath Twitter, Stack Overflow, and half the backends you have ever used. It answers millions of requests every second. And it answers them one at a time, on a single thread, on purpose. It is called Redis. Once you understand what it actually is, you start reaching for it everywhere.

Let's start in 2009. A developer named Salvatore Sanfilippo was running a small real-time analytics startup, and the database underneath it kept buckling under the load. So he built something different. The name tells you exactly what it is. Redis stands for REmote DIctionary Server. It is a dictionary — keys and values — that sits on the network, with one unusual rule. It keeps the entire dataset in memory, in RAM, instead of on disk. That is the first half of the idea.

The second half is the surprise. Redis does not just store plain text. It stores real data structures — lists, sets, counters, and more. A plain cache like Memcached hands you back whatever string you put in. Redis hands you a toolbox. That single difference is why people stop calling it a cache and start calling it a data structure server.

That choice — everything in memory — is why it is fast. There is no disk to seek, no spinning platter to wait on. Most commands finish in well under a millisecond. But the part that catches people off guard is the threading. Redis runs your commands on a single thread, one after another. The system sitting under all that traffic does one thing at a time. And that is not a weakness. It is the whole design. Because only one command runs at once, every command is atomic. No half-finished states. No locks. No race conditions to reason about. We have a name for this: single-threaded command execution. Modern versions do hand the network work to extra threads. But the data itself is always touched by one. The bottleneck was never the processor. It is memory and the network — and a single instance can still push around a million operations a second.

Here is where the toolbox earns its keep. Want a counter? One command bumps it up safely, even with a thousand clients hammering it at once. Want a leaderboard? A sorted set keeps a million players ranked in order and re-sorts them in a flash. You can count millions of unique visitors using about twelve kilobytes of memory. You can record whether every user showed up today, one bit per person. You can ask which scooters are within a mile of someone on a street corner, because Redis can index points on a map. You can even keep a durable event log that survives a restart. Each of these is a different problem in computer science. Redis turns each one into a handful of commands. The move is never just "store a value." The move is reaching for the right structure, so the hard problem solves itself.

And this is why every backend ends up here. One server can be your cache, sitting in front of a slow database and answering instantly. That pattern has a name: cache-aside. Your app asks Redis first. On a miss, it bothers the slow database, then hands the answer back for next time. Let that cached answer expire at the wrong moment, though, and a thousand requests miss at once and stampede the database. Engineers call it the thundering herd. The same server can hold your user sessions and enforce your rate limits. It can run your job queue, broadcast events between services, and hand out locks. Six separate pieces of infrastructure. One dependency. A rate limiter, for instance, is just a counter with an expiry. Increment on every request, and turn away anyone over the line. The background job systems you already lean on, like Sidekiq and BullMQ, are built on Redis. And the companies you have heard of leaned on this, hard. Twitter cached each home timeline as the last eight hundred tweet IDs in Redis, serving around thirty billion deliveries a day. Stack Overflow once took 5.8 billion cache hits in a single day, on two servers, each sitting under two percent CPU. Instagram squeezed three hundred million entries into five gigabytes. Pinterest held its entire follower graph — millions of users, billions of connections — in memory. Every counter you have watched tick up, every leaderboard you have climbed, every "seen" receipt you have ever triggered — somewhere underneath a surprising number of them sits a single-threaded dictionary in RAM, doing one thing at a time.

But there is a catch, and it is the one people forget. It all sits in memory. Pull the power, and by default, it is gone. Redis gives you two ways to save yourself, and both cost you something. It can take periodic snapshots, where a crash loses the last few minutes of writes. Or it can append every change to a log, where a crash loses about a second. There is a subtler trap, too. Replication between servers is asynchronous. So a badly timed failover can quietly drop writes your application already believed were safe. Messaging carries the same edge. Publish to a channel with no listener, and that message is gone forever. If you need it to survive, you reach for a stream instead, which keeps its history. Even locking is contested. In 2016, a Cambridge computer scientist named Martin Kleppmann picked a fight with Redis's own creator. The question: is a Redis lock actually safe enough to trust? That same year, GitHub stayed down longer than it should have, because Redis had crept into its boot path. It did not cause the outage. But the servers could not finish booting until Redis came back. The lesson is simple. Redis is a brilliant cache, and a database you have to respect.

There is one more twist, and it is recent. For its first fifteen years, Redis was open source. Anyone could use it, fork it, or build a business on top of it. But the big cloud providers were selling Redis as a paid service without giving much back. So in 2024, the company behind it changed the license to something more restrictive, and the community revolted. For a lot of teams, it raised a question they had never had to ask. Is the database we built our company on still ours to use? Amazon, Google, and Oracle took the last open version and forked it into a new project called Valkey, run by the Linux Foundation. Salvatore, who had stepped away back in 2020, came back at the end of 2024. And in 2025, Redis reversed course and shipped under a fully open-source license once more. The quiet dictionary running half the internet's backend had nearly split in two.
